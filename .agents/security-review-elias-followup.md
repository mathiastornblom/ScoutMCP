# Security review: feature/elias-followup (git diff origin/main..HEAD)

Checks run: `npx tsc --noEmit` clean; `npm run test:unit` all suites pass (elias 41/41, compat 34/34, preflight-wiring 12/12).

## Verdicts per check
1. ID handling: OK. GUID_RE/NAME_RE are ASCII-only, no `i`/`u` flag, validated BEFORE `toUpperCase()`/`toLowerCase()` (src/tools/elias.ts:28-30,50-51,613,465). A non-ASCII fold (dotless i, Kelvin sign U+212A, fullwidth) fails the regex first, so upper-casing cannot reintroduce a bypass. Every path segment goes through cseg()/seg() (validate + encodeURIComponent). Retry (elias.ts:199-211) is inside get() = GET only, fires only on 403+msgId==='grantKeyChanged', once (the retry call is not wrapped). The client's 401 relogin is bounded by isRetry (client.ts:~335).
2. elias_my_roles (elias.ts:598-618): POST to one hardcoded path, body is exactly `{containerIds}` (1-100 GUIDs, validated, upper-cased), no `mutating` flag so it is not on a mutation path and not mode-gated, no caller-controlled path/header/extra field. Output goes through wrap() (redact + cap). Cannot be used to mutate. Test asserts body shape. Note: the 401 relogin retry in doRawRequest would re-POST; harmless here (read-only, same fixed body).
3. msgId / server text: msgId is sliced to 100 chars and only compared with strict equality ('grantKeyChanged', 'containerNotFound'); never echoed. No token/cookie/URL in new messages. See F1 for the remaining echo of server message.
4. PRIVATE_401_HINT / rawRequest: hint is a static string, appended only when status 401 AND isRetry (i.e. after the single relogin). No extra login loop (login count unchanged: one per request max). No credential in text. doRequest (/rest) is untouched, so no behaviour change for other callers except the added msgId field and 401 text on raw calls.
5. Version detection: all probes are GET with fixed literal paths (`/api/v1/ui/instances`, `/api/v1/healthcheck?scoutServer=true`, `?scoutDatabase=true`); server data only selects values, never paths. sanitizeVersion limits to <=32 chars of `[0-9A-Za-z._+-]` and requires parseScoutVersion; arrays sliced (50/200). OK.
6. Redaction: all 7 new read tools run through wrap() -> redactSecrets -> capOutput; rules/capabilities passthrough is redacted + paginated + capped at 100k chars. See F2 for a residual key-name gap.
7. ourights marker: `notFoundMessageMeansAvailable` only affects interpretProbe's capability state (registry.ts / detect.ts:~128). Preflight remains proceed-on-unknown (explicit false refuses only; unchanged files src/safety/preflight.ts, ou/command/config). An attacker-controlled 404 containing "OuId not found" can only make the capability read "available" (a status/UX display); it grants nothing and removes no gate. OK.
8. No mutating ELIAS/lock tool: all 16 elias tools are GET except elias_my_roles (read-semantics POST, annotated readOnlyHint). No lock/import/delete/upload tool in src. OK.

## Findings
- F1 (Low, non-blocking) src/tools/elias.ts:172 and src/client.ts:~345: `err.message` is the server-supplied error text, echoed to the model with no length or charset limit (only msgId is capped). Pre-existing pattern, slightly widened by the 401 hint. Risk: prompt-injection or oversized text from a compromised/odd server. Repro: server returns 500 with `{"message":"<100KB text>"}` -> returned verbatim via `return err.message`. Fix: slice to ~300 chars and strip control chars in describeError's fallthrough; prefix as untrusted.
- F2 (Low, non-blocking) src/tools/elias.ts:73-90 isSecretKey: key-name matching misses `signingKey`, `accessKey`, `encryptionKey`, `authKey`, `sshKey` (only exact `key`, `apikey`, `privatekey`, `keystore`...). Short/hex symmetric keys under such names are not redacted (long base64 >=128 chars in a key-ish field is caught by the blob rule). Matters more now that rules/capabilities/container_get are generic passthrough. Fix: also redact normalised keys ending in `key` (excluding e.g. `hotkey` allow-list if needed). Repro: redactSecrets({signingKey:'abc123'}) returns the value.
- F3 (Info) elias_my_roles accepts duplicate ids within the 100 cap; harmless.

SECURITY: APPROVED
