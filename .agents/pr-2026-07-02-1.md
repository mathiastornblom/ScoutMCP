# PR 2026-07-02-1: Citrix Cloud service-principal auth (SCOUT_AUTH=citrix-cloud)

## Status
QA: APPROVED

## Summary

Branch `feature/ccauth` (18c8f24, on feature/http-transport). Adds a second auth method: OAuth2
client-credentials mint against the Citrix Cloud token endpoint (region map or `SCOUT_CC_TOKEN_URL`
override), then exchange at `/rest/auth/v1/ccauth/login` for a Scout JWT. Selected via
`SCOUT_AUTH=citrix-cloud`; password remains the default. `scout_configure` gains
`authMethod`/`cc*` inputs.

## Build / test results (independently verified)

- `npx tsc --noEmit` → PASS, zero errors.
- `npm run test:unit` → **188 passed, 0 failed**: 38+7+14+5+36+11+13+10+17+18 (prior suites, all
  green — no password/transport/OIDC regressions) + **19/19 ccauth.test.ts**, matching the claim.

## Test file review (tests/ccauth.test.ts)

- Assertions run against what the in-process HTTPS stand-in **received** (a `recorded[]` array of
  method/path/content-type/authorization/body captured server-side): mint content-type
  `application/x-www-form-urlencoded`, body parsed with `URLSearchParams` for
  grant_type/client_id/client_secret, exchange header compared exactly to `Bearer cc-token-abc123`
  (guards against `CwsAuth Bearer=`). Fully offline; self-signed cert via openssl.
- Re-mint test genuinely counts: 1 mint + 1 exchange after login, then after a forced 401 asserts
  mints === 2, exchanges === 2, and API call retried (2 hits).

## Adversarial checks (all independently reproduced)

- Missing-field combos (id only, secret only, no region, region w/o customerId, nothing): each
  yields a clear aggregated error naming exact env vars, e.g. "Missing: ccClientSecret
  (SCOUT_CC_CLIENT_SECRET); ccRegion (SCOUT_CC_REGION) or ccTokenUrl (SCOUT_CC_TOKEN_URL)". No crashes,
  no raw fetch failures.
- cc mode + username/password also set: cc wins; username/password are **not** carried into the
  config (undefined) — no hybrid state.
- `SCOUT_CC_REGION=staging` + customerId set: URL is
  `https://api.cloudburrito.com/cctrustoauth2/root/tokens/clients` — customerId silently ignored,
  no malformed URL. `missingCcFields` returns [].
- `SCOUT_CC_REGION=mars` → `Invalid SCOUT_CC_REGION "mars" — expected one of: us, eu, ap-s, jp,
  staging`. No silent US default.
- Number vs string `expires_in`: code never reads `expires_in` at all (CC token used once,
  immediately); both forms tolerated by construction.
- Exchange response missing `token` → clean `ScoutError('ccauth login response missing token')`
  (client.ts:185), no undefined-token state.
- Password regression: all prior suites green; server booted with classic env vars only —
  identical startup (auth-fail warning + successful MCP initialize handshake).

## scout_configure review

- `ccClientSecret` is never echoed: set responses return `identity` (= ccClientId), status returns
  only ccClientId/ccRegion for cc mode. Verified against 18c8f24 source.
- Cache invalidation correct: `getClient()` keys the cached instance on
  baseUrl|authMethod|username|password|ccClientId|ccClientSecret|ccCustomerId|ccRegion|ccTokenUrl,
  so switching cc → password (or between service principals) creates a fresh client.

## Observations (non-blocking)

1. No explicit test for exchange-response-missing-`token` or numeric `expires_in`; both verified
   safe by code inspection. Nice-to-have coverage.
2. `SCOUT_AUTH=password` explicit with no username/password resolves to an empty config instead of
   the classic-mode `null`; failure surfaces later at getClient/login. Cosmetic inconsistency.
3. `save=true` persists ccClientSecret to ~/.scout-mcp.json — parity with password behavior;
   flagged for Security's awareness, not a QA defect.
