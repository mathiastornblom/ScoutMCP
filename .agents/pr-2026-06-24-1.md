# PR 2026-06-24-1: Protocol hygiene — real elicitation, real notifications/progress

## Status
QA: APPROVED

## Summary

`src/elicitation.ts` replaces ad-hoc `confirm:true`-only gating with real `elicitation/create`
round-trips when the connected client declares the `elicitation` capability, falling back to
`confirm:true` otherwise. `src/progress.ts` migrates progress reporting from piggybacking on
`notifications/message` (sendLoggingMessage) to real `notifications/progress`, tied to the
request's `_meta.progressToken`.

## Adversarial checks

1. Client declares elicitation but `elicitInput()` throws — `confirmDestructiveAction()` catches
   and returns `{ proceed: false }` (src/elicitation.ts:114-123). Verified by test "a thrown
   elicitInput error fails closed." Does not crash the tool call, does not fall through to confirm-flag.
2. `accept` action with `confirmed: false` — explicitly refused (src/elicitation.ts:96-105),
   verified by test "accept + confirmed:false is refused via elicitation, even with
   confirmFlag=true." Code does not treat `action: 'accept'` alone as consent.
3. No progressToken in `_meta` — `index.ts:200-208` passes `sendProgress: undefined` to
   `createProgressReporter`, whose `report()` no-ops (src/progress.ts:78-79). Confirmed
   `device_diagnostics` (via `getProgressReporter()`) and `bulk_command` (via `ctx.sendProgress`,
   also undefined in this case) both complete without crashing — code path requires no special
   handling by either call site.
4. Progress notification duplication/stale-session risk — `index.ts` builds one `server.notification`
   closure per call from the live `server`/`progressToken` captured in that request's handler
   invocation; `device_diagnostics` reads it via the module-level `getProgressReporter()` singleton,
   `bulk_command` uses `ctx.sendProgress` directly — two different access paths to the *same*
   per-call closure, never both invoked by the same tool, so no duplication. The module-level
   singleton is reset in a `finally` block (`clearProgressReporter()`), so no stale reporter can
   leak into a later call. This relies on the documented assumption that MCP stdio handles one
   `CallToolRequestSchema` at a time with no concurrent dispatch — true for the current SDK
   request router, but worth a code comment flagging it as a single-flight assumption rather than
   an enforced invariant (non-blocking note, not a bug).

## Verdict
