## Summary of workstreams

**WS-D round 2 — five new gates on top of round 1** (`src/safety/guardrails.ts`)

- Gate 4 — Kill switch (`SCOUT_KILL_SWITCH_FILE`, default `./KILL_SWITCH`): sentinel-file check,
  fresh `existsSync` on every call, no caching. Overrides `SCOUT_MODE=write`.
- Gate 5 — Circuit breaker (`SCOUT_CIRCUIT_BREAKER_MAX_OPS` / `_WINDOW_SECONDS`): in-memory sliding
  window, module-level state, requires explicit `resetCircuitBreaker()` to re-arm (no auto-clear on
  window rollover).
- Gate 6 — Protected/allowed OU lists (`SCOUT_PROTECTED_OUS` / `SCOUT_ALLOWED_OUS`): path-segment
  subtree match (not raw string prefix), deny wins over allow. Closes the previously-documented
  target=ou blast-radius gap in `config_update` (now resolves the real device count via
  `countDevicesUnderOu` before allowing OU-scope writes), and is newly wired into `device_manage`
  (move, both source and destination), `ou_manage` (delete/move), and `move_devices_by_filter`
  (every resolved source device OU plus destination).
- Gate 7 — Private-endpoint writes hard-off in production (`SCOUT_ALLOW_PRIVATE_WRITES_IN_PRODUCTION`):
  belt-and-suspenders on top of `SCOUT_ENABLE_PRIVATE_ENDPOINTS`; only fires when `SCOUT_MODE=write`.
- Gate 8 (non-blocking) — append-only audit log (`SCOUT_AUDIT_LOG_PATH`, default
  `./logs/scout-audit.log`), newline-delimited JSON, directory auto-created, write failures swallowed
  to stderr so the audit subsystem itself can never become a denial-of-service vector.
- Gate 8b (non-blocking) — snapshot-before-mutate (`SCOUT_SNAPSHOT_DIR`, default
  `./logs/scout-snapshots`), captures effective-config payload via `writeSnapshot()` before
  fleet-scope writes; manual-restore only, no automatic rollback.

## Ad-hoc adversarial checks (step 3)

All performed via small temporary scripts placed inside the repo root (required for relative
imports to resolve under `tsx`) and deleted immediately after; no stray files left behind.

**3a. Kill switch — mid-session file creation.** Created the sentinel file *after* a successful
mutating call in the same process, then immediately issued another mutating call. Result: blocked
on the very next call, `gate=kill-switch`. Confirmed by reading `isKillSwitchEngaged()` — it calls
`existsSync(getKillSwitchPath())` fresh every invocation with no module-level cache variable
anywhere in the file. **No bug.**

**3b. Circuit breaker — cross-tool blocking and reset.** Tripped the breaker with two calls under
`SCOUT_CIRCUIT_BREAKER_MAX_OPS=1` using op names simulating "tool A", then called two more times
with op names simulating unrelated "tool B" and "tool C". Both were blocked with
`gate=circuit-breaker`, confirming the breaker is global state, not scoped to the op name or calling
tool (consistent with the single in-memory `tripped`/`opTimestamps` module variables — there is no
per-tool partitioning anywhere in the gate). `resetCircuitBreaker()` cleanly un-blocks: a call
immediately after reset proceeds. **No bug.**

**3c. Audit log content on allowed vs refused mutations.** Triggered one allowed mutation and one
refused mutation (read-only mode) through `checkMutationAllowed()` directly and read back the log.
Both entries are well-formed JSON lines with `timestamp`, `opName`, `target`, `result`, `gate`,
`actor`. **Gap found (minor):** entries written by the generic `checkMutationAllowed()` chokepoint
(Gates 1/4/5) always log `target: 'unknown'` and never populate `operation` or `blastRadius` —
those richer fields are only populated by tools that call `auditLog()` themselves with real data
(e.g. `config_update` in `src/tools/config.ts` lines 269/316-323). This is consistent and not a
correctness bug — refusals from Gate 6 (`checkOuWriteAllowed`) DO log the real OU path and
`gate:'protected-ou'` because that check builds its own `auditLog()` call with the real target — but
it does mean a kill-switch/circuit-breaker/mode refusal in the audit trail can't tell you *which*
device/OU was targeted, only that *some* mutating call was blocked. Worth a follow-up to thread the
real target through `checkMutationAllowed(opName, target?)`, not blocking for this round.

**3d. Protected OU subtree matching — sibling/prefix edge cases.** Read `isSameOrDescendant()`
(guardrails.ts:438-444) carefully: it normalizes trailing slashes, then checks exact match or
`candidate.startsWith(ancestor + '/')` — a proper path-segment boundary check, not a raw string
prefix. This correctly avoids the classic `/Foo` vs `/FooBar` false positive (verified directly via
the existing test `'a sibling OU that merely shares a string prefix is NOT blocked'`, and confirmed
by re-reading the implementation independently rather than trusting the test name). **No bug.**

**3e. Snapshot-before-mutate ordering and content.** Read `src/tools/config.ts` lines 213-234 and
292-315: `writeSnapshot()` is called and awaited (capturing real `resolveEffectiveConfig` output —
not a placeholder) strictly before the `client.request(..., { mutating: true })` call further down
the function for the same code path. Confirmed the file is written with real RSoP-shaped content
(`{target, ouPath, section, effectiveConfig}`) via the existing unit test
`'writeSnapshot creates a JSON file containing the supplied data'`, and by reading the call site —
`snapshotTarget` is the actual `resolveEffectiveConfig(...)` result, never a stub. **No bug.**

## Honesty-flag evaluation (step 4)

**4a. `countDevicesUnderOu` fails open on search errors (treats errors as 0 devices) — Severity:
MEDIUM.** Read `src/resolver.ts` lines 195-217: each OU's `/device/search` call is wrapped in its
own try/catch that returns `0` on any error, summed across the whole subtree. This makes the
blast-radius cap bypassable by anything that reliably errors the search call for some/all OUs in a
protected subtree's count — a malformed OU path is not the actual trigger (the OU is already
resolved by this point), but a flaky/overloaded Scout Board instance, a malicious or buggy
`searchTerm`/`limit` value that the live server 500s on, or a network blip during the parallel
fan-out would all silently undercount, letting an OU-scope write through the blast-radius gate when
it should have been capped or blocked. It is not a trivial-to-trigger exploit (an attacker would
need to reliably fault the search endpoint, not just supply a bad client-side path), and the
direction of the bug (undercount, not overcount) is the worse of the two possible failure modes for
a safety gate — it fails toward "allow," not "deny." The implementer's own doc comment in
`countDevicesUnderOu` already flags this honestly as "intentionally conservative in the wrong
direction for a safety gate." I agree with MEDIUM rather than HIGH because: (1) it only affects the
`target=ou` path of `config_update`, not device-level moves which use `checkOuWriteAllowed`'s
exact-path-or-descendant deny list independent of any count; (2) Gate 6 (protected-OU deny list)
still blocks writes to a *protected* OU regardless of count — this bug only weakens Gate 3
(blast-radius), not Gate 6; (3) exploiting it requires a privileged Scout Board session already
(this MCP server doesn't add a new unauthenticated attack surface). Recommend changing this to
fail-closed (treat search errors as "count unknown, block the write") in a follow-up round, since a
safety gate silently degrading to "no limit" on transient errors is the wrong default.

**4b. Response-envelope inconsistency between `device.ts`/`resolver.ts` and `workflow.ts` —
Severity: LOW for this round, confirmed non-bug for current tests/wiring.** Read both extraction
functions: `extractSearchDevices` (in `src/tools/device.ts` and duplicated in `src/resolver.ts`)
expects `{response:{status:{msg:[...]}}}` or a bare array; `extractDevices` (in
`src/tools/workflow.ts`) expects a bare array or `{Devices|devices|Items|items|Results|results|data}`.
These are genuinely different shapes with zero overlap except the bare-array case. This does **not**
cause any test to fail — the fake server in `protected-ou-wiring.test.ts` explicitly returns
`{devices:[...]}` for `/device/search` specifically because it knows `workflow.ts`'s extractor reads
that shape (see the test file's own comment at lines 164-169 acknowledging this), so the test suite
papers over the inconsistency rather than exercising it against a single real envelope shape. The
risk this poses to blast-radius/protected-OU correctness is real but conditional: `workflow.ts`'s
`resolveDistinctSourceOuPaths()` (and `countDevicesUnderOu`'s use of the *other* extractor) would
each get an empty device list if the live Scout Board's actual `/device/search` envelope matches the
shape the *other* file expects — silently undercounting affected devices or silently treating "no
source devices resolved" as "nothing to check," which would let a protected-OU move through
ungated rather than blocking it. Whether this is a live bug depends entirely on which envelope shape
the real Scout Board server returns, which I could not verify without live credentials. Recommend
confirming against a real server and unifying the two extractors (or documenting why the server
genuinely returns different shapes for what should be the same endpoint) before relying on this in
production; not blocking for this PR since round-1 and round-2 tests all pass and the existing
device_manage/ou_manage source-OU resolution path (used for single-device moves) uses
`resolveOuRef`/device-record OUID lookups, not this search-envelope path, so the most commonly
exercised flows are unaffected.
