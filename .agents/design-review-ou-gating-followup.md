# Security design review: OU-gating follow-up

Reviewed: .agents/design-ou-gating-followup.md against ou_gate.ts, devices.ts, schedule.ts, command.ts, notification.ts, openapi.json, prior findings (F1-F14). No source edited, no live access.

## Findings on the design

1. schedule_manage. The server derives the owner from the bare scheduleId, so only a list-match proof can bind id to scope. Soundness of exactly-one-integer-match is OK only if the id compared is the same value sent in the query (send the parsed integer, not the caller string). Weaknesses: (a) TOCTOU: ids are server-owned and mutable between list and write (job deleted and id reused, job re-targeted). Bounded, not removable; accept but document. (b) Scope=OU proves the job is LISTED under the OU, not that it fans out only there. A job listed under an allowed OU that also targets a protected device (devicelist job whose rows appear per receiver, or a DDG job) is exactly the residual the design names. Unverified TypeString/RootOU semantics make A unsafe to ship without the probe. (c) includeSubOus=false on get_ou may hide jobs whose RootOU is a sub-OU; that fails closed (not found), fine. (d) Fail-closed refuse-all (B) has the least surface; A is acceptable only if the probe confirms rows are attributable. There is no "add" path in the tool, correct.
2. devicelist. Design is sound in structure. Gaps: normalisation must be identical for lookup, compare and forwarded body; a server that matches ids more loosely than the gate (e.g. without braces, or case-insensitive) is handled only if the forwarded ids are the server-returned ones, which the design does. Pending/hidden/denied devices: refusing is right. 100 cap fine. Large fan-out of per-id GETs is a DoS/rate concern, not a bypass. Per-id lookup uses `clientid` query: must verify server does exact match (design compares ClientIdentifier, good).
3. ddg. Refuse-when-gated is the correct and complete choice for command/ddg. BUT the same ddg/devicelist hole exists in notification_manage (devicelist/ddg incl. devicerelocation, updatefirmware, updateuefi, delivery, DELETE) and ddg id is a QUERY parameter (`ddgid`), not body; the design's "id in body.id" statement is wrong and `id` in body is OU-ish for the sanitizer. devicerelocation via devicelist/ddg MOVES devices between OUs and its body carries destinationOU: this is higher impact than a restart, so notification_manage must not stay open. Other tools with device-list/ddg targets: grep found none outside command.ts and notification.ts (bulk_command/workflow uses per-device gating).
4. _GroupIDPath cross-check. Fail closed is right (a mismatch means the record is untrustworthy). Rename/stale-cache false refusals are acceptable and recoverable. Only comparing canonical paths is correct; do not compare names alone. Keep it strictly a refusal, never a "prefer claimed path" fallback.
5. Missing from threat model: notification_manage (above); retry/replay and idempotency of the lookup; audit of blast radius; the schedule body field in command bodies (a `schedule` key on devicelist/ddg creates future jobs, same gating as the command); env-only gates being bypassable by the lookup itself failing open; raw `body` keys beyond OU ones (F11 residual stays).

## Conditions (implementation MUST meet all)

1. Default for schedule_manage update/delete when sourceOuChecksActive(): ship option B (refuse, audited `protected-ou`/`unresolvable-source-ou`) UNLESS the read-only dev-instance probe documented in the design has been done and recorded, showing OU-, device-, devicelist- and ddg-created jobs are all attributable by `GET /schedule/ou|device`. If any job type is not attributable, B applies to that scope. DEVELOPER must not guess TypeString/RootOU.
2. If option A ships: send the parsed integer scheduleId (never the caller string) in the write query; match exactly one row with strict integer equality, otherwise refuse; msg must be an array of plain objects; for scope=device require Receiver equality with the verified ClientIdentifier; scope=OU always uses gateOuSubtree; includeSubOus normalised via subOusRequested and sent as strict boolean false; exactly one scope kind; reads allowed in dry-run; re-list immediately before the write (fresh read after any confirm prompt) and re-check the same single match; assertOuPathUnchanged before write. Document the TOCTOU residual.
3. schedule update body: sanitizeOuBody(generic:true), any ouRefs refuse, send only the sanitised schedule object.
4. devicelist: all conditions of design section 2 hold, plus: guard runs for every command under /command/devicelist (including `schedule` key, update, updateuefi, custom); normalised id = trim, strip one pair of braces, lowercase, GUID regex; reject ids with embedded whitespace/NUL/non-ASCII (no NFKC folding); de-dup on normalised form; compare normalised requested id to normalised server ClientIdentifier; forward ONLY server-returned identifiers, rebuilt as a fresh array (do not spread caller keys named clientIds in any case/variant: strip and replace, including case variants like ClientIDs).
5. devicelist lookups: any non-exactly-one result, hidden/pending/denied rows, or lookup error refuses the entire command with no POST; use one fresh resolveOuIdsFresh for the set; gateSourceOus over all distinct OUs; audit detail includes device and OU counts (no id enumeration beyond a cap).
6. devicelist: re-run resolveOuIdsFresh after any confirm prompt and immediately before the POST (not "documented residual only") for factoryreset/halt, and refuse if any source OU changed.
7. ddg: when sourceOuChecksActive(), command target=ddg is refused with audit `unresolvable-source-ou`; no override flag/env. When inactive, unchanged.
8. notification_manage target=devicelist and target=ddg MUST get the same treatment in this PR (devicelist gated via the helper, ddg refused when active), including the DELETE variants and devicerelocation (also sanitise destinationOU: for devicelist/ddg refuse any destinationOU not resolved and gated as a write target via gateOuWrite). Not deferring to a later item; README known-gaps text updated accordingly. Correct the design note: ddgid is a query param, add it to the refusal and ensure `id`/`ddgid` in body or query cannot bypass.
9. _GroupIDPath: pure check in devices.ts, comparison only in resolveDeviceSourceOus against the fresh tree; any present-but-invalid path key, path key without its id key, claimed paths disagreeing among themselves, or mismatch with the fresh path refuses (audit `unresolvable-source-ou`). Never fall back to the claimed path; absent keys unchanged. Own-property only (no prototype); undefined treated as absent.
10. No regression of F1-F14: ancestor-of-protected via gateOuSubtree, non-boolean includeSubOus via subOusRequested, all refs through one gateOuWrite, caller OU body keys sanitised, always a fresh tree. All refusals audit-logged with existing gate names; gates run after the mode check and before dry-run return and any confirm prompt.
11. When no gate is active behaviour and request count are unchanged (no extra GETs); with gates active every lookup failure refuses (never fails open).
12. Tests: every case in the design test plans implemented, plus: string/brace/uppercase/whitespace GUID variants, 100/101 id cap, mixed protected member in a devicelist, notification_manage devicelist/ddg/devicerelocation refusals, ddgid in query, and a regression that an enriched row with matching _GroupIDPath still passes. README, docs/compatibility.md and (if used) src/compat/registry.ts updated in the same PR.

SECURITY: APPROVED (with conditions)
