# PR 2026-06-22-1: RSoP engine (config_resolve) + extended config_compare + pre-write validation

## Status
QA: APPROVED

## Summary of workstreams

**WS-A — eLux config schema** (`schema/elux-config.json`, `src/schema/eluxConfig.ts`)
659 entries loaded via a cached, Zod-validated loader. `default` is `string | number | boolean | null`,
with the literal string `"unset"` used as a sentinel for "source has no documented default" (233 of 659
entries). No actual `null` defaults exist in the current dataset, but the type permits it; traced this
case manually — `null` defaults round-trip correctly through `foldConfigLayers` (`isExplicitDefault`
computed via `valuesEqual(null, null)` → true when untouched).

**WS-D round 1 — safety gates** (`src/safety/guardrails.ts`)
Three independent gates: SCOUT_MODE (read-only/dry-run/write), SCOUT_ALLOW_BASE_WRITES (base/root
write protection), SCOUT_MAX_BLAST_RADIUS (clamped to a hard ceiling). Wired into db_cleanup,
admin_manage, system_settings, device_command. 38 unit tests cover all three gates plus wiring into
each tool.

**WS-B/C — config_resolve, extended config_compare, pre-write validation**
(`src/rsop.ts`, `src/tools/config_resolve.ts`, `src/validation.ts`, diff to `src/tools/config.ts`)
`foldConfigLayers` implements the RSoP fold: factory-default seed, then layers applied in precedence
order (base → OU chain root→leaf → device), last-write-wins, with per-key `setAt`/`isOverride`/
`overridesValue`/`isExplicitDefault` provenance. `config_resolve` assembles real layers via
`buildLayersForSection` (one config_get per OU in the chain, all reads, no `mutating: true`).
`config_compare` gained four inheritance-aware modes: device-ou, device-base, ou-ou, ou-parent.
`validation.ts` validates config_update bodies against the schema before write: unknown-key (with
fuzzy did-you-mean), out-of-range, and non-fatal since-version warnings.

## Golden-file trace finding

Manually traced `tests/rsop.test.ts`'s hand-built fixture (Base → /Enterprise → /Enterprise/Boot-to-VDI
→ device) against `foldConfigLayers` independently of the test's own assertions, specifically the
"shadowing" case: `/Enterprise` sets `AuthType=2`, `/Enterprise/Boot-to-VDI` overrides to `13`.

Walking the algorithm by hand: state seeds at `{value:0, setAt:factory-default}`. The `/Enterprise`
layer sets `AuthType=2` and records `overrideHistory = {setAt:factory-default, previousValue:0}`,
state becomes `{value:2, setAt:/Enterprise}`. The VDI layer then sets `AuthType=13` and **overwrites**
`overrideHistory` with `{setAt:/Enterprise, previousValue:2}` (the value just shadowed), state becomes
`{value:13, setAt:/Enterprise/Boot-to-VDI}`. Final result: `effectiveValue=13`, `setAt=VDI`,
`overridesValue=2`.

This matches the test's expectation (`overridesValue===2`, not `0`) — and it is the **correct** RSoP
semantic: "what did this level change *from*" should reference the immediately-shadowed value in the
chain, not the root factory default. A buggy implementation that always recorded `overridesValue` as
the factory default would have failed this specific test, so the fixture is not rubber-stamping that
class of bug. I also independently traced the "isExplicitDefault when set explicitly at a non-default
level to a value matching the schema default" case (VDI sets `AuthType=0`) — `isOverride` is correctly
computed from `setAt !== 'factory-default'` (true, since it was touched) while `isExplicitDefault` is
computed independently from `valuesEqual(resolved.value, entry.default)` (true, since 0 equals the
schema default) — these are two orthogonal booleans and the implementation doesn't conflate them.
**Conclusion: the golden-file fixture reflects correct RSoP semantics, not an implementation-matching
fixture.**

## Self-reported gap classification

1. **Advanced-file-entries / files-for-transfer not separately fetched** — *Acceptable known
   limitation for this round.* Documented in `config_resolve.ts`'s `buildLayersForSection` comment;
   there's no generic Scout endpoint to enumerate these independent of a section's own config_get
   response. Correctly excluded from precedence rather than silently guessed. Recommend a regression
   test once a real endpoint/fixture is available, but not blocking.

2. **Browser\<n\>/Store\<n\>/!NETDRIVE!# sections unmapped in validation** — *Acceptable known
   limitation, but needs a regression test now.* `apiSectionToSchemaSection` and
   `schemaSectionToApiSection` both correctly treat these as no-ops (validation passes through,
   config_resolve skips them) rather than crashing or silently mismapping — verified by reading
   `schemaSectionToApiSection`'s `/[!<>#]/` guard and `validateConfigWrite`'s "no schema coverage ⇒
   valid:true" branch, both covered by an existing unit test (`"diagnostics" → null` /
   `"a section with no schema coverage... is a no-op pass"`). However there is no test exercising the
   *actual* templated names (`Browser1`, `!NETDRIVE!1`) — only a generic stand-in (`"diagnostics"`).
   Recommend adding one literal case for `Browser<n>`/`!NETDRIVE!#` before the next round, since the
   regex guard is the only thing standing between this and a wrong silent mapping.

3. **eLux-version field names guessed** — *Acceptable known limitation for this round.* Affects only
   the non-fatal since-version warning path; worst case is a missed or spurious warning, never a
   write-blocking failure or data corruption. Fine to ship, flag for follow-up once real device
   version fields are confirmed against a live server.

4. **No elicitation capability detection** — *Acceptable known limitation for this round.* Out of
   scope for §2/§3 of the spec as written; no current tool depends on it.

## Edge cases checked by reading the code (no live API calls)

- **config_resolve on a device with no OU chain at all**: `resolveTargetRef('device', ref)` throws an
  explicit `Error` ("device record had no OUPath/OUID field") *before* any layer is built — caught by
  `configResolveExecute`'s try/catch and returned as `fail(...)`. Never reaches `foldConfigLayers` with
  a null/empty ancestry. **Graceful, not a crash.**
- **config_compare ou-parent on the root OU**: `getOuChain` returns a single-element chain for the
  root (documented fallback, "never throws on a missing parent"). `configCompareInheritanceAware`
  checks `chain.length < 2` and returns a clear `fail(...)` message naming the root OU. **Graceful, not
  a crash.**
- **validation against a section with zero schema-mapped keys**: traced `foldConfigLayers([], [...])`
  directly — returns `[]` with no error (confirmed by running it standalone). `validateConfigWrite`'s
  `apiSectionToSchemaSection` returning `null` short-circuits to `{valid:true, violations:[], warnings:[]}`
  before ever calling into the per-key loop. **Graceful no-op, not a crash.**
- **isExplicitDefault when the schema's own default is `null` or the string `"unset"`**: traced by
  hand and by running `foldConfigLayers` against a synthetic entry with `default: null` — seeds
  `state.value = null` (the `e.default === 'unset'` check only special-cases the string sentinel, not
  `null`), and an untouched key correctly resolves `isExplicitDefault = valuesEqual(null, null) = true`.
  For `default: "unset"`, `isExplicitDefault` is hardcoded `false` regardless of the resolved value
  (line 134: `entry.default !== 'unset' && ...`) — by design, since "unset" means "no documented
  default to compare against," not "the default is literally the string unset." This is correct
  behavior, not a bug, but worth a one-line comment if it surprises future maintainers reading the
  results array without re-reading the source.
